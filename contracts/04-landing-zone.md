# Landing zone contract

Domain extension to OpenTofu. Load for landing zone module repositories.

- Environments are workspaces with a matching `values.<env>.tfvars`, selected by
    tooling. Never select a workspace or pass a var file by hand.
- `auto.*` files are owned externally and rewritten by the template tooling. The
    usual fix is upstream. Changing one in place is rare and ask-first, and the
    next template rewrite takes it back, so report it for the upstream change
    either way. `# init-templates: no-force` marks a template-seeded file that
    the repository owns.
- `module_graph.svg` and the generated sections of `README.md` are tooling
    output, regenerated by the `module_graph` and `tofu-docs` hooks. Write
    prose, not generated tables; fix a stale table by running the hook.
- `local.required_modules` in `main.tf` lists every child module and
    `local.module_refs` derives from it. Reference a child by
    `local.module_refs.<name>`, never a literal source. Adding an entry adds an
    external dependency, so it is ask-first.
- `module_context`, `data_context`, `alerting_context`, `backup_context` and
    `archive_context` pass through to every child module. A child that does not
    use one still declares it; that is intended, not an unused variable.
- `.trivy.tfvars` is the repository's scan fixture. Keep it valid when inputs
    change. `.auto.trivy.tfvars` is template-owned.
- `use_*` names a feature flag; `create_*` names the choice between creating a
    resource and accepting an existing one. A persistent resource you add honors
    `var.prevent_destroy`.
- Build every IAM policy with an `aws_iam_policy_document` data source, never
    inline JSON or `jsonencode`, shaping statements through `lz-iam`. The data
    source validates the structure and composes through
    `source_policy_documents`; a hand-built string does neither. This covers IAM
    policy documents only - an ECR lifecycle policy and other JSON-shaped
    arguments stay strings.
- Before adding a new input, feature or group of resources, find the matching
    template in `landing-zone-common-templates/conditional` and an existing
    consumer, and follow the pattern they establish, such as module-owned log
    groups or the KMS create-or-external-key choice. Adapt the service-specific
    details; ask where the pattern is unclear. Fix a template defect at its
    source rather than copying it.
- Do not add, change or remove OpenTofu or provider version constraints,
    including `required_providers` blocks; the templates own them. Where a
    change needs a newer version, report it for the template instead. This
    overrides *IaC → Versions*.

## Symbols

`landing-zone-common-symbols` publishes the estate's shared symbol libraries,
consumed through `language { experiments = [symbol_libraries] }`. Use them where
their semantics fit rather than redeclaring what they already define.

- Shared symbols are documented in `SYMBOLS.md` at that repository's root. Check
    the index and relevant implementations before adding a local symbol.
- A module may have one local symbol library, always imported as `this` from
    `./symbols` in a repository-owned `.tf` file. Its `*.sym.hcl` files are
    named for their concerns and form one library. It is internal to the module
    and is tested, packaged and versioned with it. Shared libraries and other
    modules must not import it directly. Extraction and shared ownership follow
    General; resource-input transformations can earn functions too.
- A packaged `this` library keeps its relative source. Pinning external shared
    libraries replaces development references to working copies, not imports
    within the module package. Local-library check triggers and index tooling
    are tracked in the common-symbols README; do not assume they already exist.
- Types and functions are `symbols::<alias>::<name>(...)`; constants are
    `symbols.<alias>.<name>`, with a dot.
- A variable typed by a library typedef documents by pointer, not by restating
    the fields.
- A typedef checks a `variable` on the way in, never an `output`. Where a module
    publishes a library-defined type as a contract, publish
    `symbols::<alias>::validate_<type>(...)`; the validator returns its
    argument, so a mismatch raises where the value is built. With nothing to
    publish, evaluate it as a `terraform_data` input. A parse result or an
    internal shape is not a published contract and needs no validator.
- A validator converts as well as checks: `optional()` attributes arrive filled
    and undeclared attributes are discarded. Never wrap a value that carries
    extra attributes onward.
- Extending a shared library changes shared code beyond the task, so it is
    ask-first unless the task is to edit the symbols library itself.

## `lz`

`lz` is the toolchain. Most of it authenticates or reaches AWS and is the user's
to run. Pass `--json` for machine-readable output and `--frozen-globals` so a
command does not regenerate the organization configuration.

These are usable:

- `lz check` - installation, toolchain and resolved context. Never `--full`,
    which opens an AWS session.
- `lz inspect modules` and `lz inspect module-graph`.
- `lz scan required` and `lz scan trivy`. Never `--plan`, which generates one.
- `lz plan changes` and `lz plan show <address>`, against a plan the user
    supplies.
- `lz tpl`, which writes only files that are absent. `-f` also overwrites, and
    is allowed once `-n` shows that no modified file would change - a
    template-owned file may still hold work the user has not yet moved to local
    ownership. Never `-F` or `--prune`; they take back hand edits and delete
    files.
- `lz environment` with no argument, which reports. Never with one, which
    switches the resolved environment.

Everything else is the user's, including `tofu`, `two-step`, `access`, `aws`,
`login`, `ecr`, `outputs`, `secrets`, `permissions`, `ci`, `init`, `customer`,
`config`, `commit`, `lock`, `upgrade`, `run` and `repo cleanup`. They
authenticate, read or mutate live state, publish, rewrite sibling checkouts, or
delete saved plans.

## Monitoring

`alerting_context` defines where alerts go. Its `channels` are keyed by
severity, from `symbols.C.alerting.levels`. Never create an SNS topic,
subscription or EventBridge target of your own for an alert.

- Where the module README has no `## Monitoring and Alerting` section, a change
    also covers the module's existing resources and adds that section. Keep the
    section current: one brief note per alert saying what it detects, its
    severity and what an admin should check first.
- `use_alerting`, on by default, switches all of a module's alerts. The
    `alerting` object holds each alert's `level` and, for metric alarms, its
    threshold. Setting `level = null` switches that alert off. This works the
    same way for metric, event and log alerts. An alert that is added but
    switched off defaults to `level = null`.
- With `use_alerting` on, a module that creates alerts fails on a `null`
    `alerting_context`. A `null` context is for bootstrapping and for modules
    without alerts.
- Metric alarms: `cloudwatch-metric-alarms`, with `levels` naming the severity.
- Event alerts: `event-bridge-filter` rules with the `alerting` block, targeting
    `alerting_context.sns_topic_arn_event_bridge` with
    `sns_submission_role_arn`. `event-bridge-alerting` is the reference.
- Log alerts: the `alerting` key of a `local.log_groups` entry from the
    `log_group` template, which sends to `local.log_alert_arn` and names the
    filter `<severity> // <group> // <title>[ // <description>]`. `group` is a
    key of the group mappings in `lambda-log-alert`. Title and description are
    fixed text without `:` or `*`, which AWS rejects in filter names.
- Central alerting over OAM (`use_oam_alerting`, tagging with
    `alerting_context.oam_alerting_tags`, rules in `cloudwatch-oam-alerting`)
    suits only clear-cut failures that need no configuration and benefit from
    one central rule, such as a tagged Lambda failing. A new central alert
    changes `cloudwatch-oam-alerting`, so it is ask-first. If a resource
    carries `alerting_context.oam_alerting_tags`, the central OAM rule is
    responsible for alerting on it. Do not add a local alert for the same
    failure. If the resource does not carry the tags, add the local alert.
